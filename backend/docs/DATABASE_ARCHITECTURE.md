# JALDRISHTI Database Architecture

This document describes the persistence layer for the JALDRISHTI inundation modeling framework as implemented in Milestone 14.

## PostgreSQL & PostGIS Role
The framework uses **PostgreSQL** for relational data persistence and **PostGIS** for spatial geometries. This replaces the early-stage temporary file-based JSON stores and hardcoded mock data.
- **PostgreSQL**: Stores metadata about simulations, dams, glacial lakes, scenarios, and execution states.
- **PostGIS**: Provides `Geometry` types for dams, lakes, and simulation domains. The standard CRS is **EPSG:4326** (WGS 84). We do not mix projected and geographic coordinates silently.
- **GeoAlchemy2**: Integrated with SQLAlchemy to provide ORM support for PostGIS functions like `ST_AsGeoJSON`.

## Database Tables
- `dams`: Contains dam metadata (height, capacity) and `POINT` geometry.
- `glacial_lakes`: Contains glacial lake metadata (volume, depth, area) and `POINT` geometry.
- `scenarios`: Stores model parameters for reproducible runs (JSON).
- `simulations`: Tracks lifecycle and execution state, referencing generated spatial artifacts.

## File/Object Result Storage
Heavy spatial data generated by the hydrodynamic solvers (GeoTIFFs, KML, SHP packages, GeoJSON polygons) are **NOT** stored directly in PostgreSQL to prevent database bloat. Instead, the `simulations` table contains precise local file paths (which could easily be adapted to S3/Blob storage URIs).

## Migrations and Seeding
An explicit migration and seeding mechanism is provided in `backend/scripts/migrate.py`. This script:
1. Provisions all missing tables.
2. Seeds `Idukki Dam` as reference data.
3. Seeds `South Lhonak Lake (Sample)` with rigorous provenance tags.

## Development Setup without Docker
Because development environments may lack Docker:
1. A local PostgreSQL database can be installed on Windows/Linux natively.
2. The PostGIS extension must be installed (`CREATE EXTENSION postgis;`).
3. Connection details are sourced from `backend/.env` (`database_url`).
4. If the database is completely unavailable, the API will intentionally and clearly fail (`HTTP 503`), preventing silent fallbacks that hide missing persistence. 
5. During tests, tests that strictly rely on PostgreSQL/PostGIS will `SKIP` gracefully if the database cannot be reached, allowing hydrodynamic solvers to still be unit tested independently.

## Security Considerations
- Parameterized queries provided strictly via SQLAlchemy ORM (mitigates SQL injection).
- No arbitrary filesystem path traversal from frontend (API endpoints only use UUID-based simulation resolution).
- No hardcoded database credentials.
